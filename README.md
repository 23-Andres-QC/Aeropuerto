# AeroVision · analítica espacial de personas por sitio

Plataforma para Lima Airport Partners: transforma video de cámaras en trayectorias anónimas sobre un plano 2D y, a partir de ellas, en indicadores operativos y comerciales. Funciona igual para cualquier **sitio** (LAP · Jorge Chávez, ESAN o uno nuevo): cada sitio tiene su plano calibrado, cámaras, locales, zonas y las sesiones que procesa el modelo.

```
CCTV / dataset → Modelo LAP01 (Python, GPU) → API Go → PostgreSQL/PostGIS → Web Vue
                 Parte I   tracking local
                 Parte II  Re-ID multicámara + mapa 2D      → sessions, identities, tracklets, trajectory_points
                 Parte III histórico e insights             → zone_id, spatial_events, session_analytics
```

## Ejecutar

```bash
scripts/levantar.sh
```

El mismo comando sirve en la laptop y en el servidor: el script reconoce si corre en la VM de Google Cloud y toma la configuración de cada lugar.

| | Laptop | Servidor (VM de Google Cloud) |
|---|---|---|
| Configuración | valores por defecto de `compose.yaml` | `servidor.env` (versionado) |
| Web | http://localhost:8080 · https://localhost:8443 | http://IP-pública · https://IP-pública |
| Cámara web | https://IP-de-la-laptop:8444 | https://IP-pública/camara/ |
| Modelo en vivo | fuera de Docker, con la GPU | en la laptop, con su GPU, por un túnel SSH (`python scripts/modelo_local.py`); el servidor solo tiene la web |
| Contraseñas de las bases | las de demostración | aleatorias en `.env` (las crea el script la primera vez) |
| Acceso a la web y a la API | usuario `LAP`, contraseña `LAP` (de prueba) | usuario, contraseña, firma de sesiones y llave de scripts aleatorios en `.env` (el script los crea y muestra la contraseña una vez); la API no arranca sin ellos |

En el servidor la IP pública se lee de la propia VM en cada arranque, así que si cambia al encenderla basta volver a correr el script. `.env` (no versionado) tiene prioridad sobre `servidor.env` para ajustes de una sola máquina; ver `.env.example`. En la laptop también funciona `docker compose up -d --build` directamente.

**Modelo en la laptop, web en el servidor.** `python scripts/modelo_local.py` (con el compose local detenido) abre un túnel SSH a backend-vivo (8093) y al MJPEG de camara-web (8092) del servidor, que ahí solo escuchan en 127.0.0.1, y corre `camara_telefono.py` con la GPU contra ellos: Teléfonos y Videos funcionan igual que con el modelo en el servidor. Los teléfonos se unen en `https://IP-pública/camara/`; su video baja por el túnel y las cajas, IDs, género y memoria de identidades vuelven al servidor. Entra siempre con la contraseña del servidor, que lee de `SERVIDOR_CLAVE` en el `.env` de la laptop (no versionado; sin ella la pide una vez); `MODELO_SERVIDOR=usuario@IP` apunta a otro servidor. Se recupera solo: rehace el túnel si la conexión se corta o queda colgada (la prueba cada 10 s), espera al servidor si está arrancando y vuelve a levantar el modelo si se cae. Requiere `pip install paramiko`. Con un enlace lento (~1 MB/s) el modelo recibe menos cuadros por teléfono, pero salta cuadros en vez de atrasarse. Para volver al modelo en CPU dentro del servidor: `COMPOSE_PROFILES=modelo` en su `.env`.

Web en http://localhost:8080 (usuario y contraseña de prueba de la laptop: `LAP` / `LAP`; en el servidor, los que creó `levantar.sh`; ver «Seguridad»). Cada sección es la misma para todos los sitios: `/sitios/<sitio>/en-vivo`, `/sitios/<sitio>/insights` y `/sitios/<sitio>/configuracion`, con pestañas para cambiar de sitio. `/telefonos` procesa cámaras de teléfono en vivo y `/videos` prueba el modelo con un video de tu computadora, sin guardar nada.

Los datos se conservan en el volumen `aeropuerto-demo_pgdata`. La base se crea vacía con dos sitios (ESAN y LAP) y **sin datos de ejemplo**: todo lo que muestra lo publica el modelo o se configura en la web.

## Flujo de trabajo

1. **Procesar un dataset (Partes I y II).** `Modelo/Build Modelo/Build_Modelo.ipynb` procesa los videos de `Modelo/dataset/` (YOLO26m, seguidor local, YOLO26s-ReID, mapa 2D y género con CLIP), exporta a `Build Modelo/Ouput/` y publica la sesión en el sitio `SITIO` (`POST /api/v1/sites/<sitio>/sessions`): plano calibrado, cámaras, identidades, tracklets y cada punto de trayectoria.
2. **Configurar el plano (web → Configuración).** Mover y girar cámaras arrastrándolas, registrar y editar **locales**, eliminar sesiones y dibujar sus zonas **INTERIOR** (ingreso) y **FRONTAGE** (frente), más zonas operativas (pasillo, entrada, cola, check-in, seguridad, puerta). Todo se guarda en PostGIS; volver a publicar el Build no pisa una cámara movida a mano.

   El **dibujo del plano** (fondo SVG de `web/public/planos/`, contorno exacto del piso y **obstáculos**: la huella de lo que nadie atraviesa, como la carpa o una máquina) se guarda aparte del Build (`PUT /api/v1/sites/<sitio>/plano`). El de ESAN sale de un levantamiento desde las cámaras: `Modelo/Build Modelo/plano_esan/levantamiento.json` marca píxeles del suelo (murete, descanso bajo el entrepiso, tramo de la L que sube al norte, puertas de los ascensores, carpa azul, expendedoras, tacho, reciclaje) y `generar_plano.py` los pasa a metros con las homografías del Build. El 100 % de los puntos de cam01 y cam02 y el 99,6 % de los de cam03 caen dentro de ese piso.

   ```bash
   python "Modelo/Build Modelo/plano_esan/generar_plano.py" --publicar --zonas
   ```

   `--zonas` crea las zonas de `zonas_iniciales.json` (Ascensores, Tacho, Reciclaje y los locales Carpa azul, Expendedora negra y Expendedora roja, cada uno con su zona INTERIOR: llegar a una expendedora cuenta como una visita) solo si el sitio aún no tiene zonas; después se editan desde la web.
   **Zona grabada 2 (el comedor del Edificio D).** Es otra zona del mismo ESAN, no otro sitio: las dos se ven en un solo mapa, el del campus. Su dibujo (`web/public/planos/esan-zona-2.svg`) viaja como una *capa* del plano de ESAN (`plano.capas`: el dibujo, su escala, su ubicación y giro, su contorno y obstáculos, en los metros del patio), y sus zonas son zonas de `esan` con esas mismas coordenadas. Sale del plano de evacuación S-05 (2.º piso, enero 2018), enderezado de una foto y trazado en `Modelo/Build Modelo/plano_esan/zona2/generar_zona2.py`; su escala (29,7 px/m) se ajusta a las áreas reales del cuadro del plano y su ubicación sobre el campus es aproximada. `python "Modelo/Build Modelo/plano_esan/zona2/generar_zona2.py"` regenera el SVG y `zona2/capa.json` y compara las áreas dibujadas con las del plano; luego `generar_plano.py --publicar` guarda la capa con el plano de ESAN y `generar_zona2.py --zonas` crea los locales y zonas que falten (Comedor, Comedor de profesores, Zona de atención, escaleras, SS.HH., depósito y cuarto de data). En el mapa, **Ver campus** muestra las dos zonas y un clic en la segunda (o su botón) acerca a ella. Todavía no tiene cámaras ni sesiones: nada simulado.

3. **Procesamiento histórico (Parte III).**

   ```bash
   python "Modelo/Insights Modelo/insights_historicos.py" --sitio esan
   ```

   Lee de la base los puntos de la sesión, el plano y los locales y zonas configurados. Primero lleva cada posición al **piso transitable**: la que cae fuera del piso o dentro (o a menos de 0,2 m) de un obstáculo pasa al punto libre más cercano, y si dos cámaras promedian dentro de un obstáculo se unen fuera de él; la base guarda la posición ajustada (En vivo e Insights la usan) y conserva la del modelo en `raw_x`/`raw_y`. Después calcula: consolidación de observaciones simultáneas, zona de cada posición (INTERIOR primero, luego la de menor área), eventos espaciales (EXPOSURE, ENTER, DWELL, EXIT, RETURN, QUEUE; una salida o un roce del INTERIOR más corto que la tolerancia de 1 s se trata como ruido del borde), mapa de calor KDE (ocupación y visitantes únicos), rutas frecuentes con PrefixSpan, grafo origen-destino, permanencia, visitas, exposición, tasa de captación, densidad, congestión y las series por intervalo del tablero. Lo publica en `trajectory_points.zone_id`, `spatial_events` y `session_analytics`. Parámetros versionados en `Modelo/Insights Modelo/config_insights.json`; `--exportar` guarda además CSV/JSON en `Insights Modelo/Ouput/<sitio>/`. Vuelve a ejecutarlo cada vez que cambies locales o zonas: Insights avisa cuando el análisis quedó desactualizado.
4. **Ventas y pronóstico (web → Ventas).** Ver abajo, «Ventas, emparejamiento y pronóstico».
5. **Ver resultados (web → En vivo / Insights).** En vivo reproduce la sesión sobre el plano con los videos sincronizados; Insights es un tablero de métricas (mapas de movimiento y de calor, comparación entre zonas, rutas, personas, visitas, exposición, permanencia, captación, densidad, entradas por intervalo y flujos), filtrable por sesión y zona y exportable a PDF y CSV.

**Cámaras en vivo (separadas del demo).** Tienen su propio backend (`backend-vivo/`) y su propia base (`vivo-db`, PostgreSQL + pgvector); los sitios LAP y ESAN siguen en el backend y la base de siempre. `app-web/` convierte el navegador de cualquier teléfono en cámara, sin instalar nada: se abre `https://<IP-de-la-laptop>:8444`, se pulsa **Unirse con la cámara** y la cámara se registra sola en **Teléfonos**, que muestra todas las pantallas conectadas con el proceso del modelo (cajas, ID, género, personas, fps y latencia). `python "Modelo/Test Modelo/camara_telefono.py"` corre el modelo final en la GPU sobre todas a la vez (detector a 960 px y confianza 0,15 para ver a quien está lejos; en CPU usa yolo26s a 640 px, que es unas 1,6 veces más rápido que yolo26m a 480; las cajas salen de yolo26s-pose: se arman con cabeza, hombros, caderas, rodillas y tobillos, sin los brazos, y desde arriba quedan en la cabeza (`MODELO_POSE=ninguno` vuelve al detector normal); detectar y seguir van en un carril rápido que publica las cajas enseguida, y género, Re-ID y memoria de identidades van en un carril lento aparte, así las cajas no esperan a lo más pesado; los IDs se sostienen con los mismos ajustes de Videos) (el seguidor abre tracks desde 0,3 de confianza, no 0,6; mientras el género no se confirma con 2 votos de CLIP se muestra el que va ganando desde el primer voto, sin guardarlo) y guarda una **memoria de identidades**: cada persona conserva su ID (y su color) aunque salga y vuelva, pase a otro teléfono o el modelo se reinicie. Se guarda solo su apariencia como vectores Re-ID y cuándo y dónde se vio (nada de video ni fotos, y **ya no su género**); se borra sola tras 24 horas sin verla o con **Olvidar a todos** en Teléfonos. Detalles en [backend-vivo/README.md](backend-vivo/README.md) y [app-web/README.md](app-web/README.md).

**Al apagar En vivo, el modelo olvida a todos.** Con **● EN VIVO · Salir** (o al elegir una sesión guardada) la captura se guarda por última vez y, ya guardada, se vacía la memoria de identidades (lo mismo que **Olvidar a todos** en Teléfonos): al volver a prender En vivo los IDs empiezan en 1 y cada persona se identifica como nueva. Mientras En vivo sigue prendido, la memoria se conserva (quien sale y vuelve mantiene su ID).

**Insights en vivo cuenta a todos los identificados.** Una persona solo entra al plano si su teléfono se ubica (su cuadro se parece a una referencia de su cámara); si no, antes Insights quedaba en cero aunque el modelo la viera con ID, y En vivo mostraba esa cámara como apagada, sin aviso. Ahora Insights la cuenta (personas, género, cuánto se vio, sin recorrido ni zonas) y avisa cuántas no se ubicaron, y En vivo avisa qué cámara no reconoce el patio.

**Conteo por sentido (para validar).** En vivo cuenta, en cada cámara, quién cruza una línea a media altura del cuadro (punteada en amarillo sobre el video de cada cámara): **suben** los que la cruzan hacia arriba de la imagen (se alejan de la cámara) y **regresan** los que la cruzan hacia abajo. Cuenta cada track del modelo por su pie, tenga o no ID y se sepa o no su género (con banda de ±6 % para que el temblor de la caja no sume cruces); quien sube y vuelve cuenta en los dos sentidos. Bajo cada cámara se ve «↑ suben · ↓ regresan»; Insights trae la tabla por cámara y sentido con Hombre, Mujer, Sin determinar, con ID y sin ID (el género sigue el mínimo de grupo del sitio, que se baja en Configuración), el CSV la exporta y la captura la guarda en su `summary.conteo_direccion`, así Insights la muestra también al abrir una captura guardada.

**ID y género más rápidos, en paralelo.** El modelo en vivo corre tres carriles: el rápido (detectar y seguir: las cajas), el de los IDs (Re-ID y memoria de identidades) y el del género (CLIP), estos dos en hilos aparte y en paralelo (antes el género esperaba al Re-ID en el mismo hilo). Una persona nueva recibe su ID a los 0,6 s visible (era 1 s; 2 s si se parece a alguien ya visto, eran 3), y como cada ID nuevo se sigue comparando 60 s con los antiguos, si era alguien ya visto vuelve a su ID. El género se muestrea cada 0,3 s (era 0,6) y queda fijo en cuanto 2 votos llegan a 0,8 de certeza; si no, se sigue probando hasta 10 cuadros (antes se decidía con 3 y, sin certeza, el track quedaba sin género para siempre). Medido con los videos del dataset como dos teléfonos: el género pasa de 1,27 s a 0,73 s (mediana) y de 87 % a 90 % de las personas con género.

**Marcador en vez de caja, y Re-ID y género con la parte de arriba del cuerpo.** Sobre el video (la página del teléfono, Teléfonos, En vivo y Videos) cada persona lleva un palito sobre la cabeza con un punto de su color y, al lado, su ID global y su género (quien aún no tiene ID, el palito gris sin etiqueta): ya no una caja que la tapa. El modelo nunca dibujó las cajas (manda solo sus coordenadas y las dibuja el navegador), así que esto no cambia su velocidad. El Re-ID y CLIP ven solo la mitad de arriba de cada persona (cabeza, pelo y torso): las piernas se parecen entre la gente y con el teléfono cerca salen cortadas, y el Re-ID estira cada recorte a un cuadrado, donde la mitad de arriba llega menos deformada. Con los videos del dataset quedó a la par del cuerpo entero; `MODELO_PARTE_SUPERIOR=1` vuelve a él. Las vistas Re-ID ya guardadas en la memoria son del cuerpo entero: conviene **Olvidar a todos** (o apagar En vivo) al empezar a probar.

**Detectar siempre a la persona (desde arriba o con el cuerpo cortado).** YOLO ya veía a quien se graba desde arriba (casi solo cabeza y hombros, confianza ~0,2) o de cerca con las piernas fuera del cuadro (~0,45), pero los umbrales de después lo perdían: el seguidor abría tracks recién desde 0,25 (no aparecía su marcador) y el Re-ID tomaba vistas desde 0,5 (no recibía ID). Ahora el seguidor abre desde 0,15 y el Re-ID toma vistas desde 0,35; lo que no se mueve sigue oculto y un track pide 3 detecciones seguidas. Medido con los videos del dataset como dos teléfonos: de 32 a ~40 personas seguidas en 2 min, con algo más de cambios de ID (de ~20 a ~30, con mucho ruido de una corrida a otra). `MODELO_CONF_TRACK` y `MODELO_CONF_REID` cambian esos umbrales.

**El mapa en vivo va con la cámara.** En vivo ubica a la gente en el plano 10 veces por segundo (eran 4) y el punto casi no se suaviza (antes, en cada vuelta se movía solo la mitad de lo que faltaba): iba ~0,4 s detrás de lo que mostraba la cámara. El calor y el tiempo en cada zona suman el tiempo real entre vuelta y vuelta. Y con teléfonos en vivo, los videos subidos (Videos) avanzan a lo más 5 pasadas por segundo: detectar varios videos a 1280 px les quitaba GPU a los teléfonos, que se atrasaban y se cortaban mientras se procesaba un video.

**Video parejo y las mismas cajas en todas las cámaras.** La página de la cámara manda con cada cuadro la hora en que lo tomó, y Teléfonos lo muestra a esa hora y no a la de su llegada: la Wi-Fi del teléfono entrega los cuadros a ráfagas y, mostrados al llegar, el video repetía esos tirones. Además se pueden tener hasta 4 cuadros sin acuse (eran 2): un corte de ~150 ms de la Wi-Fi ya no detiene la cámara. El atraso del video (para que cada cuadro vaya con sus cajas) es uno solo para todas las cámaras, el percentil 90 de lo que tardan sus cajas (era el 75: la cámara más lenta llevaba 1 de cada 4 cuadros con cajas adivinadas y las otras casi ninguno), y se mueve solo si se aleja más que una banda; si sobra mucho salta de una vez. Medido con tres teléfonos simulados con la Wi-Fi a ráfagas: de ~50 a ~22 cortes de más de 120 ms por minuto y cámara, ninguno de más de 200 ms, ningún cuadro saltado y ~93 % de los cuadros de cada cámara con sus cajas, a cambio de ~70 ms más de atraso.

**En vivo: cámaras al costado y unión por posición.** En modo en vivo el plano queda a la izquierda y a su derecha van los dos teléfonos (cam01 y cam02, las cámaras con referencias para ubicarlos en el plano; cam03 es solo la del video grabado) con su video, cajas, IDs y género, más la lista «Ahora mismo». Si el Re-ID del modelo le da IDs distintos a la misma persona en cámaras distintas, la casilla **Unir personas muy cercanas** (encendida por defecto) muestra como una sola a quien dos cámaras distintas ubican a menos de 1,2 m (promedia lo que ubica cada una, con más peso a la que la ve más grande; nunca une dos IDs que ve una misma cámara y mantiene la unión hasta 1,8 m y 3 s para que no parpadee). Con IDs distintos por cámara: dos personas sin la casilla, una con ella.

**Elegir el sitio (ESAN, LAP).** La tarjeta de arriba a la izquierda es un selector: al pulsarla (o con ↓ estando enfocada) se abre la lista de sitios, con las flechas se elige, Enter confirma y Esc o un clic fuera la cierra. Las pestañas de sitio sobre el contenido y «Cambiar a …» de Ctrl+K llevan al mismo lugar. Se queda en la misma sección (En vivo, Insights, Ventas…); si el sitio elegido aún no tiene cámaras ni capturas, como el aeropuerto **LAP · Jorge Chávez** (por ahora su plano de 546 × 978 m y su configuración), abre **Configuración**, donde están su mapa, sus zonas y sus cámaras, en vez de pantallas vacías. La lista de sitios se pide al iniciar sesión (la API exige login) y se vacía al salir.

**Paleta de comandos (Ctrl+K).** Ctrl+K (⌘K en Mac, o «/» fuera de un campo, o el botón *Buscar…* de la barra) abre una búsqueda sin tildes ni mayúsculas para saltar a una sección, a una pestaña de Ventas, a las ventas de una tienda o de un período (`?locales=2,3` y `?dias=7` también funcionan en la dirección), a otro sitio, y para activar el modo en vivo, cambiar el tema o cerrar sesión. Recuerda lo último que se usó.

**Videos (probar el modelo sin guardar nada).** En **7. Videos** se elige un video de la computadora y se ve cómo lo procesa el modelo final en tiempo real: el video se reproduce a su velocidad normal con las cajas, el ID y el género encima, más FPS del modelo, ms por frame, personas y avance. El video va un poco detrás del modelo (unas décimas a 1,5 s, según su ritmo) y en cada cuadro de pantalla cada caja se interpola entre los dos frames procesados que rodean ese instante, así acompaña a la persona en vez de saltar detrás de ella (`web/src/features/videos/interpolacion.ts`). Si el modelo se atrasa, el video espera en lugar de adelantarse. El archivo se sube tal cual a backend-vivo, que lo guarda en disco temporal (nunca en una base) mientras el modelo lo procesa. El modelo lo lee con OpenCV a su resolución original, sin recomprimir ni redimensionar antes de procesarlo. Al terminar se borran las dos copias del archivo y queda a la vista el **resumen**: personas contadas, reparto por género, cada persona con su ID, su género y en qué segundos del video aparece, duración, tiempo de proceso, FPS y ms por frame promedio, frames procesados y el último frame con sus cajas. El resumen vive en la memoria de backend-vivo hasta que se pulsa **Quitar video**, que lo borra; quitar el video mientras se procesa lo detiene sin dejar resumen. Lo procesa el mismo servicio que los teléfonos (`camara_telefono.py`, en la laptop o en `modelo-vivo`), pero con un motor y un asociador propios: no toca la sesión de los teléfonos ni la memoria de identidades. Los ajustes son más sensibles que los del Build, pensados para cualquier video y no solo para las cámaras de ESAN: Se eligen varios a la vez (desde un teléfono, de su galería) y se suben todos juntos, cada uno con su barra; el modelo los procesa al mismo tiempo: un hilo lee y detecta el frame que toca de cada video en una sola pasada de YOLO mientras el lazo principal sigue, re-identifica y publica la pasada anterior, con un hilo por video. Con tres videos de 15 fps, cada uno pasa de 10,1 a 12,4 cuadros procesados por segundo. Antes se subían de a uno y el modelo se turnaba un frame de un video por pasada. Además, ningún video de más de 1 MB llegaba a subirse: la verificación de la sesión de nginx (`/_autenticar`) comparaba el tamaño del cuerpo con su límite de 1 MB y respondía 500.

- **Detector:** 1280 px en la GPU (en CPU, la del Build), con confianza 0,10 y media precisión: en un video de un centro comercial pasa de unas 12 a unas 40 personas por frame. `VIDEO_IMGSZ` fija otra resolución.
- **Seguidor:** abre tracks desde 0,15 de confianza, acepta personas desde 12 px de alto y olvida en pocos segundos a quien se fue. Re-ID y género muestrean a cada persona una vez por segundo.
- **IDs estables:** con recortes chicos el Re-ID es ruidoso. El asociador corta una identidad solo con 3 vistas seguidas muy distintas y une más fácil a quien reaparece; el seguidor recupera a quien perdió un momento con menos parecido. En un video de un centro comercial: de 70 a 58 identidades en 25 s, sin cortes.
- **Lo quieto no cuenta:** maniquíes, afiches o estatuas que el detector toma por personas. Si en 4 s a la vista no se alejan más de un 20 % de su altura de donde aparecieron (descontando el movimiento de la cámara), no se dibujan ni se cuentan. Quien se mueve una vez cuenta para siempre. Una persona que se queda totalmente quieta todo ese tiempo también se oculta.
- **IDs:** se confirman con 3 vistas y 2 s a la vista.
- **Género:** se muestra desde la primera vista, con la certeza promedio de CLIP, en vez de «Sin determinar» hasta juntar votos. En el Build y en las cámaras en vivo el género se fuerza a Hombre o Mujer con 2 votos de CLIP (55 % de certeza, personas de 72 px o más); «Sin determinar» queda solo para quien nunca tuvo una vista con evidencia suficiente (`gender` en `config_lap01.json`).
- **Sin GPU (servidor):** sin los puntos del cuerpo de los teléfonos, Re-ID y género cada 2 s por persona y Re-ID con todos los núcleos; el movimiento de la cámara se mide sobre el fondo (fuera de las personas) para que los maniquíes no parezcan moverse. En un video de un centro comercial: de ~570 a ~240 ms por frame.

Con mucha gente el modelo va a unos 3–4 FPS en una RTX 4060. El video se ve fluido igual, pero las cajas se actualizan menos seguido. A cambio de detectar a casi todos, hay más falsos positivos y géneros menos seguros en las personas lejanas. Los valores están en `AJUSTES` de `Modelo/Test Modelo/videos_subidos.py`. El modelo procesa en tiempo real, como una cámara en vivo: si no alcanza al video, salta frames. Se pueden elegir varios videos a la vez (hasta 10 en la lista, de hasta 1 GB cada uno): el modelo los procesa todos al mismo tiempo, turnándose un frame de cada uno, y la página muestra el estado de cada uno (preparando, procesando o terminado) y el video o el resumen del que se elija. Con más videos a la vez, las cajas de cada uno se actualizan menos seguido (`VIDEOS_SIMULTANEOS` limita cuántos).

## Ventas, emparejamiento y pronóstico

La sección **Ventas** (`/sitios/<sitio>/ventas`) responde tres preguntas: cuánto se vende en cada local, **quién compró qué y a qué precio**, y cuánto se ganará en los próximos días. Todo queda en PostgreSQL (migración `008_ventas.sql`).

- **Tickets (`sales_tickets`, `sales_items`).** Un ticket es una compra en un local a una hora; sus líneas guardan producto, categoría, cantidad y precio unitario, y el total es la suma exacta (en centavos). Se cargan uno a uno, con un **CSV de la caja** (`ticket;fecha_hora;local;producto;categoria;cantidad;precio`, hora de Lima, coma o punto y coma) o por la API. El número de ticket de la caja evita duplicados al volver a cargar un archivo. Un local con ventas no se puede borrar.
- **Datos reales y simulados.** Cada ticket lleva `origin = REAL | SIMULADO`. **Generar ventas simuladas** (pestaña Datos) crea semanas de tickets y de visitantes por hora para ver los gráficos sin una caja conectada; todo queda marcado como simulado, la web avisa cuando se mezclan con lo real y se borran de una vez. La semilla depende del sitio: la misma demo sale igual cada vez.
- **Emparejamiento persona ↔ compra (`sales_matches`).** La Parte III ya dice quién estuvo dentro de cada local y cuándo (eventos ENTER y EXIT de la zona INTERIOR). Cada ticket se asigna a la persona cuya estadía cubre la hora de la venta o terminó justo antes (tolerancia de 90 s entre el reloj de la caja y el de las cámaras; pagar antes de entrar puntúa más bajo que pagar al salir). Una persona paga una vez por visita y un ticket tiene una sola persona; se asignan primero las parejas más probables. Cada pareja guarda su **confianza**, que baja cuando varias personas podían ser quienes compraron. Se corre desde la pestaña Emparejamiento (la demo también lo corre) y no guarda nada personal: solo el número anónimo de la persona.
- **Pronóstico.** Holt-Winters aditivo con tendencia amortiguada sobre el historial por día (patrón semanal) o por hora (patrón diario), para ingresos, tickets y visitantes; de ahí salen la conversión y el ticket promedio esperados. Los pesos de suavizado se eligen probando una grilla y quedándose con los que mejor predijeron cada punto a partir de los anteriores; esos mismos errores dan la banda del 80 % y el «error típico» que muestra la web. Con menos de dos semanas de historial no puede aprender el patrón semanal y usa solo nivel y tendencia; con menos de 4 puntos no proyecta. Los productos se proyectan manteniendo su parte de las últimas 4 semanas.
- **Elegir en el plano.** Un clic en una tienda ve solo esa; un clic en un **área** (cualquier zona que no sea de un local: un pasillo, una sala, una puerta) ve todas las tiendas que tiene dentro, y las áreas pueden contener a otras (terminal ⊃ sala ⊃ tienda). A la derecha, las mismas áreas y tiendas en lista para afinar la selección. Todo lo de Ventas (resumen, pronóstico, tickets) se calcula sobre lo elegido; la API lo recibe como `locales=1,2,3`.
- **Lo que importa (pestaña Resumen).** El panel lee los números y los dice en palabras: cómo van los ingresos frente a los mismos días de antes y qué los mueve (visitantes, conversión, ticket promedio), el local que convierte poco y cuánto dejaría de vender si convirtiera como el resto, el local que rinde más de lo que le toca por la gente que recibe, los días que se salieron de lo habitual de su día de la semana, el producto que más deja y cuánto de lo vendido se sabe quién lo compró. Las tarjetas muestran la flecha de variación contra el período anterior (se lee el doble de días y se parte por la mitad). La lógica está en `web/src/features/ventas/lecturas.ts`.
- **Cuándo se vende.** La pestaña suma las ventas y visitas por día de la semana y hora (hora de Lima, `GET /ventas/patrones`) y dibuja la semana como un mapa de calor de 7 × horas, para ingresos, visitantes, tickets o conversión, con el mejor momento, el mejor día, cuándo entra más gente y una **oportunidad**: la franja con mucha gente y poca compra, con lo que se dejaría de vender. Debajo, **un día típico sobre el plano**: el reloj recorre el día y cada tienda emite un halo que crece y se enciende según lo que tiene a esa hora (promedio de los días del período, de un día de la semana o de todos), con el ranking de locales reordenándose. Con pocos días de datos avisa que el patrón es poco confiable.
- **¿Y si…? (pestaña Pronóstico).** Un simulador: se mueven los visitantes, la conversión o el ticket promedio (o se elige una situación: campaña, promoción, subir precios, combos) y se ve cuánto cambiarían los ingresos esperados, con su rango probable y lo que aporta cada cambio. Es la cuenta ingresos = visitantes × conversión × ticket (la conversión no pasa de 100 %): sirve para comparar escenarios, no adivina cómo reaccionaría la gente (`simulador.ts`).
- **Recorrido hasta la compra (pestaña Emparejamiento).** El botón **Recorrido** de cada pareja dibuja sobre el plano por dónde caminó esa persona: el trazo se parte en lo que hizo antes de entrar al local, dentro de él y después, con el pin del momento del pago, y se reproduce caminando. Los tiempos se miden desde el inicio de la sesión (a mitad de cada estadía la persona queda dentro de la zona de su local). Si el ticket cae fuera de la estadía, avisa que la pareja es poco segura (`recorrido.ts`).
- **Movimiento.** Los gráficos se dibujan de izquierda a derecha (con un punto que guía el trazo; el botón ↻ lo repite), los números de las tarjetas suben hasta su valor, las barras crecen y las filas de las tablas entran una tras otra. Se apaga solo con «reducir movimiento» del sistema. Código en `web/src/features/ventas/` (`animar.ts`, `components/CifraAnimada.vue`, `components/GraficoSerie.vue`).
- **Los visitantes** salen de los ENTER del modelo (cada persona cuenta una vez por local y hora) y, en la demo, de `visit_counts`. Si hay más tickets que visitantes, la web avisa: las cámaras no ven entrar a todos.

## Tráfico por período (PR 1)

**Insights → Tráfico por franja y fecha** (y `/api/v1/sites/<sitio>/trafico/…`) responde, para un período, una franja horaria y unos datos (reales, simulados o todos): dónde estuvo la gente, cuánto se quedó y cuántos entran y compran. Se calcula **en el backend (Go)** a partir de las posiciones guardadas de cada sesión (migración `009_trafico.sql`).

- **Cómo se cuenta (igual que la Parte III).** Las posiciones de cada persona se consolidan en una por instante de 0,2 s (ponderadas por la confianza del detector, sin saltos imposibles), cada posición toma la zona en que cae (INTERIOR primero, luego la menor) y los tramos seguidos en una zona forman una **estancia** (una salida de menos de 1 s es ruido del borde). Cada estancia se cuenta en la ventana donde empieza. `domain/traffic_calc.go` replica `Modelo/Insights Modelo/historico`; una prueba con 8 personas sintéticas procesadas por la Parte III real (`tests/generar_paridad.py` → `testdata/paridad_parte3.json`) exige los mismos tramos, eventos y totales.
- **Agregados por ventana.** `traffic_buckets`: por zona y ventana de **5, 15 y 60 minutos**: personas distintas, visitas (estancias), cuántas personas **se detienen** (estancia ≥ 5 s) y cuántas quedan **interesadas** (≥ 30 s), y un histograma de permanencia (14 tramos). `heat_cells`: segundos-persona por celda de 1 m y hora. `traffic_runs` guarda cuándo se calculó cada sesión. Lo real pertenece a una sesión; lo simulado no tiene sesión y lleva `origin = SIMULADO`.
- **Se recalcula solo.** Una sesión nueva, la Parte III al publicar, una zona o tienda editada o un umbral cambiado dejan lo calculado desactualizado; una pasada en segundo plano lo recalcula (cambiar los umbrales recalcula antes de responder). `POST …/trafico/recalcular` fuerza una pasada (`?todo=1` recalcula todas las sesiones). La web dice «calculando…» mientras tanto.
- **Zonas y tiendas (Configuración).** El editor de la zona elegida tiene **tipo** (ahora con **Descanso**, una sala de espera) y **tienda**: interior y frente exigen tienda. Un panel **Tiendas** crea, renombra, categoriza y elimina tiendas (eliminar una se lleva sus zonas de interior y frente). Un panel **Umbrales de tráfico** edita «se detiene» e «interesado» por sitio (la forma guardada deja lugar a umbrales por tipo de zona, pero hoy un solo juego vale para todos).
- **Mapa de calor por franja y fecha.** Período rápido (7, 28, 90 días o todo) o fechas, franja (mañana, tarde, noche u otra, en hora de Lima) y datos. El color es segundos de presencia por hora en cada celda y la escala es la del día completo del mismo período, así las franjas se comparan a simple vista.
- **Permanencia.** Histograma con mediana, el 90 % y el porcentaje que supera cada umbral, para el interior de las tiendas, una tienda (interior o frente) o una zona; los umbrales se cambian ahí mismo. La mediana y el 90 % salen del histograma (error de hasta el ancho del tramo); la media y los porcentajes son exactos.
- **Embudo por tienda.** Pasan por el frente → se detienen → entran → compran (los tickets de la caja del mismo período; todavía no se enlazan con cada persona). Si la tienda no tiene zona de frente, la web pide dibujarla **en vez de mostrar un 0**; si algún paso trae más gente que el de arriba, lo avisa.
- **Tráfico simulado de varias semanas** (Ventas → Datos, o el botón del aviso «sin datos»). Parte de los visitantes por tienda y hora de las ventas simuladas (los que entran son esos), calcula cuántos pasan según la tasa de captación de cada tienda y dibuja cada estancia con una permanencia propia del tipo de lugar; todo marcado **SIMULADO**, separable con el filtro «Datos», con las mismas ventanas y umbrales que lo real. Generarlo crea (o reemplaza) las ventas simuladas de las mismas semanas; borrar las ventas simuladas borra también su tráfico.
- **Hora de inicio de la grabación (`INICIO_GRABACION`).** El Build **exige** declararla para publicar (si falta, avisa antes de procesar y bloquea la publicación, y el backend rechaza un BUILD sin `recording_start_declared`; una hora en el futuro también). Una sesión que nunca la declaró (como la de ESAN, de antes de esta regla) se marca **hora estimada** en Registros e Insights y se corrige desde Registros → *Corregir hora* (`PUT …/sessions/{id}/inicio`: mueve todos los tiempos de la sesión y borra sus emparejamientos con ventas, que hay que volver a correr).
- **Comparar con la Parte III.** `node scripts/comparar_trafico_parte3.mjs esan` contrasta, zona por zona, personas, permanencia, visitas y exposición del backend con lo que guardó la Parte III y sale con error si algo difiere.
- **Retención.** Vectores de apariencia 24 h, puntos crudos 90 días, agregados sin límite: ver «Cuentas y privacidad» (la limpieza automática ya corre; estos agregados sobreviven a los puntos crudos).

Cada migración nueva tiene su reversa en `backend/migrations/down/` (fuera de lo que se aplica al arrancar); una prueba aplica la reversa y vuelve a aplicar la migración.

> **Roles por módulo, recuperación de contraseña por correo y seguridad:** ver [docs/acceso-y-seguridad.md](docs/acceso-y-seguridad.md) (matriz de permisos, cómo crear el superadmin, cómo configurar el SMTP y la checklist).

## Cuentas y privacidad (PR 2)

**Cuentas en la base.** `users` (migración `012_cuentas.sql`) guarda cada cuenta con su contraseña como hash **argon2id**; nunca la contraseña. Hay dos roles: **superadmin** (ve y hace todo) y **tienda** (ve solo las cifras de su local; puede haber varias cuentas por tienda). No hay registro público: las crea el admin en **8. Cuentas**, que entrega una **contraseña temporal una sola vez** (no se escribe en ningún log ni en la bitácora) y obliga a la persona a elegir una propia en su primer ingreso (12 caracteres como mínimo, no su usuario, no un solo carácter repetido). Restablecer la contraseña, desactivar o borrar una cuenta cierra sus sesiones en el acto; nadie puede desactivarse ni borrarse a sí mismo, ni se puede quedar la plataforma sin un admin activo.
- **Cuenta semilla.** El primer admin sale de `ADMIN_USER` / `ADMIN_PASSWORD` (en la laptop, `LAP` / `LAP`): se crea al arrancar y, mientras su dueño no cambie la contraseña, sigue a las variables de entorno (un `ADMIN_PASSWORD` nuevo toma efecto al reiniciar y cierra sus sesiones). Cuando la cambia desde la web, la base manda.
- **Sesiones.** La cookie `lap_sesion` (HttpOnly, SameSite=Strict, Secure por HTTPS) lleva un secreto al azar; la base guarda solo su SHA-256, así **revocar vive en la base y sobrevive a un reinicio**. Un admin se desconecta tras **8 h sin usarla o 3 días como máximo**; una tienda, **8 h fijas**. Cambiar la contraseña cierra las demás sesiones. `SESSION_SECRET` y `SESSION_HOURS` ya no existen.
- **Bloqueo.** Además del límite por IP, 8 contraseñas equivocadas bloquean la cuenta 15 minutos. El mensaje de un login fallido no dice si el usuario existe.
- **Lo que ve una tienda.** Solo `GET /sites/<su sitio>/trafico/permanencia` y `/embudo`, con el local **fijado por el servidor** a su local (pida el que pida), más `/auth/me` y cambiar su contraseña. **Todo lo demás responde 404** (no debe ni enterarse de que existe), y En vivo, las cámaras y el panel de personas responden 403 en el nginx. En la web, una tienda ve una pantalla sencilla (**Mi tienda**: pasan, se detienen, entran, compran y cuánto se quedan) sin el menú del análisis, y nunca personas, cámaras ni género. (El portal completo de la tienda llega en el siguiente paso.)
- **La llave de los scripts** (`API_KEY`, rol `maquina`) sigue igual: lee y escribe, **nunca borra** (403) y no administra cuentas (403). Sale de las variables de entorno.
- **Llave de ingesta por tienda.** En **8. Cuentas** se crea una llave por tienda (`lapk_<prefijo>_<secreto>`): se muestra una vez, la base guarda su hash, se puede revocar, y solo identifica a su tienda (la ingesta de datos de ventas llega en el siguiente paso; hoy solo sirve para `GET /auth/me`).
- **Bitácora.** `audit_log`: inicios de sesión, cuentas creadas, restablecidas, desactivadas o borradas, llaves, el sitio Demo y la retención; con quién, qué y desde qué IP. Nunca lleva una contraseña, una llave ni un código.

**Unir teléfonos con un código (QR).** En **6. Teléfonos** el admin pulsa **Crear código de unión**: se muestra como QR (se dibuja en el navegador) y como texto `XXXX-XXXX`. **No vence ni tiene tope de teléfonos**: el mismo código sirve siempre para cualquier teléfono hasta que el admin lo revoque, y se guarda en el volumen `camara-datos`, así sobrevive a reiniciar o reconstruir el servicio (la página del teléfono lo recuerda y, si el servicio se reinició, se vuelve a unir sola con él); el código y la clave van en el **primer mensaje del WebSocket** (nunca en la URL, así no quedan en los registros del nginx) y el QR lo lleva en el fragmento de la dirección (`#c=…`), que no viaja al servidor. Cada teléfono recibe **su propia clave** para reconectarse sin código; el admin puede **revocar el código** (no se une nadie más; los ya unidos siguen) o **un teléfono** (se desconecta, sale de Teléfonos y no vuelve ni con un código vigente). Un código malo cuenta como intento fallido: 10 desde una IP la bloquean 15 minutos. Las cámaras unidas y sus claves viven en memoria del servicio de cámara web (`app-web/`).

**El género ya no se guarda por persona.** Dónde estaba: `identities.gender_estimate/confidence/votes` en la base de los sitios (lo escribía el Build al publicar), `personas.genero` junto al vector de apariencia en la memoria de backend-vivo, `identidades_genero.csv` en lo que exporta el Build, y se mostraba por persona en Registros/Replay, en Ventas (emparejamientos) y En vivo. Ahora:
- Al publicar una sesión el backend **cuenta** (`session_gender_counts`: cuántas personas de cada género) y descarta el género de cada una; la migración `011_genero_agregado.sql` convirtió lo que ya había en conteos y quitó las columnas. En backend-vivo la migración `002_sin_genero.sql` quitó `genero` de `personas` (el modelo lo sigue mandando y se ignora). `identidades_genero.csv` no se sirve por la API, y la reproducción, la Parte III y Ventas ya no traen género por persona.
- **Grupos de al menos 5.** Un conteo por género solo muestra las categorías con 5 personas o más; el total sí se muestra. Si ocultar una sola categoría permitiera deducirla (total menos las visibles), se oculta también la menor de las visibles hasta que lo oculto sea de 5 o más. Ejemplo: 20 H, 9 M y 1 sin determinar muestran solo «20 H» y «10 sin desglosar». ESAN (6 H, 3 M, 7 s/d) muestra solo «7 sin determinar». La misma regla vale en la pantalla para lo que no se guarda (En vivo). El criterio está en `domain.PrivateGender` (Go) y en `suprimirGenero` (web), con las mismas pruebas. **El 5 es un ajuste por sitio** (`sites.min_group_size`, migración `014_grupo_minimo.sql`, de 1 a 50): un superadmin lo cambia en **Configuración → Privacidad del género** (`PUT /sites/{sitio}/grupo-minimo`), cada cambio queda en la bitácora y, por debajo de 5, el panel de género avisa «Desglose con grupos pequeños: solo para pruebas». **La cuenta de una tienda usa siempre 5**, sin importar el ajuste, y la regla de que nada oculto se deduce restando vale con cualquier mínimo.
- **En vivo** sigue mostrando el género de cada persona (el modelo lo calcula en el momento), pero solo al **admin**: el nginx cierra En vivo, Teléfonos y la sala con 403 a una tienda, y nada de eso se guarda.

**Retención.** Vectores de apariencia **24 horas** (backend-vivo los borra solos; `RETENCION_HORAS` pasó de 168 a 24), puntos crudos **90 días**, conteos y promedios sin límite, bitácora 1 año. Una pasada diaria (y **Depurar ahora** en Cuentas) borra los puntos de las sesiones de más de 90 días **cuyo tráfico ya se agregó** (una sesión sin agregar se conserva y se avisa) y las marca (`sessions.points_purged_at`) para que el tráfico no se recalcule sobre puntos que ya no están y vacíe sus agregados: por eso cambiar los umbrales de tráfico ya no cambia lo calculado de una sesión depurada. Los eventos espaciales (ENTER, etc.) y los análisis por sesión se conservan. El **Aviso de privacidad** está en `/privacidad` (se abre sin sesión, desde el login) y en la página de la cámara.

**Sitio Demo.** En **8. Cuentas → Crear el sitio Demo** (`POST /api/v1/demo`) se arma un sitio aparte («Demo (simulado)», marcado `demo`) con un plano pequeño, tres tiendas, 8 semanas de ventas y tráfico simulado, **todo SIMULADO**: sirve para demostraciones sin tocar los datos de un sitio real como ESAN, al que no se le genera nada simulado. Solo un admin puede borrarlo, con `DELETE /api/v1/demo?confirmar=<nombre>` (la web pide escribir el nombre del sitio); se lleva ventas, tráfico, sesiones, cuentas y llaves de sus tiendas.

Cada migración tiene su reversa en `backend/migrations/down/` (y la de backend-vivo en `backend-vivo/migrations/down/`), con una prueba de deshacer y rehacer; el género por persona no se puede recuperar al deshacer.

## API

Todas las rutas de sitio siguen `/api/v1/sites/<sitio>/…`:

| Método y ruta | Uso |
|---|---|
| `POST /api/v1/auth/login` · `POST /auth/logout` · `GET /auth/me` · `POST /auth/password` | inicio y cierre de sesión (cookie HttpOnly), quién está conectado y elegir una contraseña propia; ver «Seguridad». **Todas las demás rutas piden sesión o llave de API** |
| `GET/POST /usuarios` · `POST /usuarios/{id}/clave` · `PUT /usuarios/{id}/activo` · `DELETE /usuarios/{id}` · `GET /auditoria` | cuentas (la clave temporal se entrega una vez), restablecer, activar/desactivar, borrar y la bitácora. **Solo superadmin** |
| `GET/POST /sites/{sitio}/tiendas/{local}/llaves` · `DELETE …/llaves/{id}` | llaves de ingesta de una tienda (la llave completa se muestra al crearla, una vez). Solo superadmin |
| `GET /privacidad` · `POST /privacidad/depurar` | la retención vigente y su estado, y aplicarla ahora. Solo superadmin |
| `POST /demo` · `DELETE /demo?confirmar=<nombre>` | crea y borra el sitio Demo (todo SIMULADO). Solo superadmin |
| `/camara-web/api/codigos` · `/camara-web/api/dispositivos/{teléfono}` | (cámara web, por el nginx y solo para el admin) códigos de unión: crear, listar y revocar; revocar un teléfono |
| `GET /api/v1/sites` · `POST` · `PUT/DELETE /{sitio}` | sitios (se borra solo un sitio sin sesiones) |
| `GET /{sitio}/config` | sitio, plano calibrado, dibujo del plano, cámaras, locales y zonas |
| `PUT /{sitio}/plano` | dibujo del plano: fondo `/planos/*.svg`, contorno del piso y obstáculos en metros |

## Seguridad

La web y la API piden iniciar sesión, con cuentas en la base y dos roles (ver «Cuentas y privacidad (PR 2)»). Qué hay y cómo se usa:

- **Login en el servidor.** `POST /api/v1/auth/login` con `{"usuario","clave"}` deja la cookie `lap_sesion`: un secreto al azar (la base guarda solo su SHA-256), **HttpOnly** (ningún script de la página la lee), **SameSite=Strict** (otro sitio no puede mandarla) y **Secure** cuando la web se sirve por HTTPS; un admin se desconecta tras 8 h sin usarla o 3 días, una tienda a las 8 h. `POST /auth/logout` la **revoca en la base**, así una copia de la cookie deja de servir también tras un reinicio de la API. `GET /auth/me` dice quién eres. Además, las peticiones que cambian algo y vienen de otro origen se rechazan.
- **Qué responde sin sesión.** Solo `/health/live`, `/health/ready` y el login. Todo lo demás de `/api/` responde **401**, incluidas las lecturas. nginx también cierra `/vivo/` (backend-vivo: teléfonos, videos y memoria de personas), la sala de cámaras (`/camara-web/ws/sala`, que muestra el video de todos los teléfonos) y `/camara/personas`, preguntándole al backend (`auth_request`).
- **Roles.** `superadmin` puede todo; `tienda` solo ve su local (todo lo demás, 404; En vivo y cámaras, 403). Los scripts usan la **llave de API** (`Authorization: Bearer <API_KEY>`, rol `maquina`): leen y escriben pero **nunca borran** (un `DELETE` con la llave da 403) y no administran cuentas (403). Todo borrado se registra en el log con quién, desde qué IP y cómo terminó.
- **Scripts de Python** (Build, Parte III, `generar_plano.py`): mandan la llave que encuentran en `LAP_API_KEY`, o en `API_KEY` del `.env` de la raíz, o la de prueba de la laptop. Con otra, la web responde 401 y el script avisa qué falta.
- **Límites.** nginx limita por IP: el login a 5 intentos por minuto, la API a 30 por segundo y la puerta pública de las cámaras (`/camara/`) con su propia cuota (20 por segundo y 30 conexiones). Además el backend bloquea 15 minutos a una IP tras 5 logins fallidos seguidos (también con la clave correcta).
- **Credenciales.** En la laptop (`APP_ENV=local`, lo normal) valen las de prueba `LAP` / `LAP` y una llave de prueba; la API lo avisa en su log. En el servidor (`APP_ENV=servidor`, de `servidor.env`) **no arranca** con las de prueba ni con credenciales débiles (`ADMIN_PASSWORD` de 12 o más caracteres, `API_KEY` de 24 o más): `scripts/levantar.sh` las crea al azar en `.env` la primera vez, muestra la contraseña una sola vez y conserva el `.env` que ya existía (solo agrega lo que falta). No se escriben en ningún log ni en la web.
- **Lo que sigue público, a propósito.** La página `/camara/` y su WebSocket, para que un teléfono se una sin iniciar sesión: solo GET, sus cinco archivos (con el Worker que comprime los cuadros) y el WebSocket, nada del MJPEG, la foto ni el estado. **Riesgo conocido:** cualquiera que alcance esa URL puede mandar video como si fuera una cámara; y el puerto 8444 de la cámara web existe para que los teléfonos de la misma Wi-Fi se unan a la laptop: sirve solo la página y su WebSocket (el panel de personas, el video y el estado no salen por ahí), y en el servidor ni siquiera se publica (`CAMARA_BIND_ADDR=127.0.0.1` en `servidor.env`; los teléfonos entran por `/camara/`). **Ya no basta la URL:** un teléfono se une solo con un código de unión (no vence, sirve para cualquier teléfono) que crea el admin; sin él, el WebSocket responde un error y no registra nada.
- **Aún no hay:** doble factor, recuperación de contraseña por correo (la restablece el admin) ni la ingesta de datos de las tiendas.
- **Fuentes de prueba: nada falso en la base.** `node scripts/simular_telefonos.mjs` simula dos teléfonos con una persona caminando (para probar En vivo sin teléfonos; `--ids distinto` prueba la unión por posición) y los registra siempre con `simulado: true`. En vivo muestra lo que ven (con «PRUEBA · no se guarda» y «(prueba)» en sus mosaicos), pero ninguna captura que los incluya se guarda: ni al terminar, ni al reiniciar, ni sola cada 30 s. La marca se queda aunque el teléfono se desconecte a mitad de la captura. Las pruebas de Go con base de datos usan una base desechable (`aeropuerto_test`) y se niegan a correr en otra. Si registras a mano una cámara de prueba (por ejemplo el video de `Modelo/Test Modelo/simular_telefono.py`), pasa `"simulado": true`.

## Modelo de datos

PostgreSQL 17 + PostGIS, coordenadas del plano en metros (SRID 0), tiempos con zona horaria. `sites` (plano calibrado del Build y dibujo del plano, en JSON) → `cameras`, `locales`, `zones` (polígono, área calculada, INTERIOR/FRONTAGE ligadas a un local) → `sessions` → `identities` → `tracklets` → `trajectory_points` (posición sobre el piso transitable y la original del modelo en `raw_x`/`raw_y`, geom calculada, `zone_id` de la Parte III), `spatial_events` (duración calculada) y `session_analytics` (KDE, rutas, origen-destino, métricas y parámetros). El tráfico vive en `traffic_buckets` (por zona y ventana de 5/15/60 min), `heat_cells` (celdas de 1 m por hora), `traffic_params` (umbrales por sitio) y `traffic_runs` (cuándo se calculó cada sesión); `sessions.recording_start_declared` dice si alguien declaró cuándo empezó la grabación. `session_gender_counts` guarda cuántas personas de cada género tuvo una sesión (nunca el género de cada una). Las cuentas viven en `users`, `auth_sessions` (solo el hash de la cookie), `store_api_keys` (solo el hash de la llave) y `audit_log`. Ninguna tabla guarda imágenes, recortes ni embeddings.

## Despliegue en un servidor

Por defecto la web se publica solo en `127.0.0.1`. Para servirla por la IP pública, crea un `.env` con:

```bash
BIND_ADDR=0.0.0.0
WEB_PORT=80
WEB_TLS_PORT=443
PUBLIC_HOST=<IP pública del servidor>
DB_PASSWORD=<una contraseña propia, no la del ejemplo>
VIVO_DB_PASSWORD=<otra contraseña propia>
# Solo si el servidor es ARM (ej. GCP c4a): postgis/postgis no tiene imagen arm64.
DB_IMAGE=imresamu/postgis:17-3.5
# Modelo en vivo en CPU (servidor sin GPU) y enlace público para unir teléfonos.
COMPOSE_PROFILES=modelo
ENLACE_CAMARA=https://<IP pública del servidor>/camara/
MODELO_CPUS=7        # núcleos para el modelo (deja uno para la web)
MODELO_IMGSZ=640     # resolución del detector en CPU (por defecto 640 con yolo26s; 480 va más rápido pero ve peor a lo lejos)
```

El modelo en vivo (`modelo-vivo`) necesita los pesos de CLIP que van por Git LFS: en el servidor, `git lfs install --local && git lfs pull` antes de construir.

y levanta con `docker compose up -d --build`. nginx añade `nosniff`, `SAMEORIGIN`, `Referrer-Policy` y un límite de peticiones por IP sobre `/api/`; PostgreSQL y el backend no publican puertos al host.

- **Acceso:** la web y la API piden iniciar sesión y el servidor no arranca con credenciales de prueba (ver «Seguridad»); `scripts/levantar.sh servidor` crea `ADMIN_USER`, `ADMIN_PASSWORD` y `API_KEY` al azar en `.env`. Si armas el `.env` a mano, agrégalos y pon `APP_ENV=servidor` (ya está en `servidor.env`). Para un uso real conviene servir por HTTPS: la cookie solo marca `Secure` cuando la página llega así.
- **Cámaras del navegador y teléfonos:** los navegadores solo dan acceso a la cámara en `localhost` o HTTPS (la web también escucha en `WEB_TLS_PORT` con un certificado autofirmado). La cámara web (`app-web`) se sirve además por el nginx de la web en `https://<IP>/camara/`, así en el servidor basta con abrir 80 y 443 en el firewall.
